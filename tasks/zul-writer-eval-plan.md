# zul-writer 端到端評測計畫

> 取代 `zkidea/tasks/zul-writer-skill-test-plan.md` 的 Layer B。Layer A（命令列合約，20 項檢查）維持不變且全綠。
>
> 本計畫自 08-25 起存放於 `agent-skill`，與它所測的技能、設計稿、驗證器、測試套件同一個 repo。

---

# L1：執行摘要

## 核心目標

用 `ui-screenshots/` 的設計稿，讓 AI 完整跑一次 `zul-writer`（設計稿 → 頁面 → 控制器 → 預覽自審），
然後**獨立驗證產出**，並找出這個流程本身有什麼問題。

**產出的是「流程缺陷清單」，不是頁面評分。** 頁面好不好看不是本計畫的問題；流程哪裡卡住、哪裡
指示不清、哪裡工具讓事情變難，才是。

## 里程碑

| Phase | 名稱 | 狀態 |
|---|---|---|
| P0 | 前置就緒：對照組與檢查套件可用 | **完成** |
| P1 | 題目與檢查表定稿 | 未開始 |
| P2 | 執行四次跑動 | 未開始 |
| P3 | 三重驗證（機械／盲判／人工） | 未開始 |
| P4 | 綜合為變更提案 | 未開始 |

## 總體進度：20%（P0 完成，P1–P4 未開始）

## 三個必須先講清楚的結論

1. **驗證方法本身必須先被驗證。** AI 判 AI 有共用盲點，所以 P3 內含**負對照**：故意餵一組
   不相符的「設計稿＋成品」給判定者。**判定者若沒抓到，該輪所有判定作廢。** 抓不到錯的檢查
   等於沒有檢查。
2. **對照組不再使用展示頁。** 展示頁會被重新產生（這正是你刪掉那兩個檔的原因），因此改用專用
   素材當成功路徑的對照組。此決定已執行完畢，變更緣由見 L3。
3. **技能自己教出了一個重複三次的缺陷，已修在源頭。** `--` 註解錯誤的成因是技能的參考文件
   建議 Java 的 `// ---` 分隔線，卻沒說 XML 不許。修正已完成並提交，因此 P2 的四次跑動
   同時成為這個修正的實測：**再出現一次就是修正無效**，而不是新發現。

# L2：階段進度

**名詞統一**：「設計稿」= `ui-screenshots/` 的 PNG；「成品」= 跑動產生的 `.zul` 與控制器；
「預覽圖」= `preview-zul.py` 輸出的 PNG；「受測者」= 執行技能的代理；「判定者」= 驗證的代理。

## P0 — 前置就緒（完成）

* **目標**：讓成功路徑有一個永不變動的對照組，且既有檢查套件可用。
* **輸入**：既有的命令列合約套件。
* **輸出**：專用對照素材一份；套件指向它。
* **執行步驟**
  1. 新增專用對照素材（刻意最小、合法、零版面發現、高度足夠）。
  2. 把套件的對照組指向它，不再指向任何展示頁。
* **驗收標準（已達成）**
  * 對照素材在視窗寬 1280 與 1600 兩種情況下**都無版面發現**。
  * 全頁擷取的高度**大於**視窗高度，證明摺線以下確實接圖。
  * 檢查套件 **20 項全過，離開碼 0**。

## P1 — 題目與檢查表定稿

* **目標**：把「跑一次技能」變成四次可互相比較的跑動。
* **輸入**：`ui-screenshots/` 九張設計稿。
* **輸出**：四份受測者題目；一份結構化檢查表；一組負對照。
  **三者一律寫入 `tasks/eval-private/`（已列入 `.gitignore`）** —— 受測者讀得到本 repo，答案卷不得進版控。
* **執行步驟**
  1. 選四張設計稿。**依「條件」而非「張數」選**：一張 2 倍匯出、一張非儀表板版型、
     兩張儀表板。排除已有成品的兩張，餘七張可用。
     為何是四張而非七張：2 倍匯出與非儀表板版型各**只有一張**設計稿支援，張數再多也無法
     增加；剩下五張全是儀表板，多跑三張等於重複同一個條件，而每次跑動的成本是一整輪
     產生＋渲染。**明說這是取樣上限，不是全覆蓋**；是否加跑第二批由 P4 的驗收標準決定。
  2. 寫四份題目。**三份把 Step 1 的答案先寫進題目**（ZK 版本、MVC 或 MVVM、靜態或模型驅動），
     讓 Steps 2–5 可比較；**一份刻意不答**，只給圖說「做出來」。
  3. 寫結構化檢查表：只問結構，不問美感。每題必須是**是／否**，且能指著圖說出依據。
  4. 準備負對照：一組刻意配錯的「設計稿＋預覽圖」。
* **驗收標準**
  * 檢查表每一題都能只看兩張圖回答，不需要看程式碼或逐字紀錄。
  * 檢查表中**沒有任何**涉及顏色、字距、間距美感的題目。
  * 四份題目中，Step 1 被預先回答的那三份，答案完全一致。

## P2 — 執行四次跑動

* **目標**：取得四組成品、預覽圖與逐字紀錄。
* **輸入**：P1 的四份題目。
* **輸出**：每次跑動一份 `.zul`、一份控制器、一張預覽圖、一份逐字紀錄。
* **執行步驟**
  1. 每次跑動使用**獨立的受測者**，寫入專用的評測目錄。
  2. 受測者**不得**看到本計畫、檢查表、或其他跑動的結果。
  3. 環境先備妥：本機 launcher jar、專案已編譯。
* **驗收標準（機械可驗，無需判斷）**
  * 產出的 `.zul` 通過驗證器四層檢查。
  * 預覽**離開碼 0**，且確實產生 PNG。
  * 逐字紀錄可取得，且能從中讀出：跑了哪些 Step、傳了哪些參數、渲染幾次。
  * 四次跑動**互不知情** —— 任一次的逐字紀錄中不得出現其他跑動的檔名。
  * **`--` 註解錯誤零次出現。** 四次跑動都在修正後的準則下執行；任一次再犯，代表源頭修正
    無效，該項退回 P4 重新立案。

## P3 — 三重驗證

* **目標**：判斷成品是否符合設計稿，且判斷本身可信。
* **輸入**：P2 的成品、預覽圖、逐字紀錄；P1 的檢查表與負對照。
* **判定者的模型**：判定者必須跑在**與受測者不同、且更強的模型**上（Fable 5），受測者則
  維持一般使用者手上的預設模型。強判定者對上普通受測者是刻意的不對稱：技能是給真實使用者
  用的，受測條件要貼近現實，而檢查條件不必。這降低「兩邊犯同一個錯而都看不出來」的機率，
  但**不消除** —— 同一家族仍共享部分盲點，所以負對照與人工抽驗不因換模型而省略。
* **輸出**：每次跑動一份機械數據列、一份盲判結果、兩次人工抽驗結論。
* **執行步驟（順序不可調換）**
  1. **機械驗證**：從預覽輸出與 JSON 報告抽出客觀數據 —— 版面發現數、實際使用的視窗寬度、
     設計稿寬度、渲染次數、控制器狀態。全部可覆核，不含判斷。
  2. **負對照先跑**：把配錯的那組交給判定者。
  3. **盲判**：判定者**只看**設計稿與預覽圖，逐題回答檢查表。**不得**看到逐字紀錄。
  4. **流程驗證**：現在才讀逐字紀錄 —— 問了什麼、假設了什麼、第一次渲染後改了什麼。
  5. **人工抽驗**：四次中挑兩次，由人並排看設計稿與預覽圖，給出結論。
* **驗收標準**
  * **負對照必須被判為不符。若判定者放它過關，本輪盲判全部作廢，重寫檢查表。**
  * 人工抽驗的兩次結論與盲判結論**一致**。若不一致，另兩次的盲判結論不予採信，
    並改為全部人工抽驗。
  * 機械數據中，「實際視窗寬度 vs 設計稿寬度」一欄對四次跑動都有值。

## P4 — 綜合為變更提案

* **目標**：把觀察變成可執行的變更。
* **輸入**：P3 的三組結果。
* **輸出**：排序後的流程缺陷清單，每項附對應的變更提案。
* **執行步驟**
  1. 蒐集摩擦項：受測者繞過的每一件事、看似讀了兩次的指示、工具讓事情變難的地方。
  2. **依「跨跑動重複次數」排序** —— 出現一次是軼事，重複才是訊號。
  3. 每項提案標明它是技能指示的問題、工具的問題、還是文件的問題。
  4. `--` 註解項**不列入本次缺陷清單** —— 成因已定位、修正已提交，它現在是 P2 的受測項，
     不是待提案項。只有 P2 又出現，才以「修正無效」重新立案。
* **驗收標準**
  * 每項提案都指名**是哪幾次跑動**觸發的。
  * 只出現一次的觀察，明確標為「軼事，待再觀察」，不得寫成結論。
  * **若「只出現一次」的項目多於「重複出現」的項目，就從剩下三張儀表板設計稿加跑第二批**，
    直到重複項不再增加。四張是檢查點，不是終點。

# L3：技術附錄

## 已知的方法論限制

* **判定者與受測者仍共用部分盲點。** P3 已改為跨模型（判定者 Fable 5，受測者維持預設），
  但同家族模型若系統性誤讀某種版型，受測者做錯、判定者仍可能說對。換模型降低機率、不消除，
  因此 P3 的人工抽驗與負對照仍是唯一防線。
* **比對兩張圖正是技能自己在 Step 5 做的事**，因此評測與被評測共用同一種失效模式。
  這是檢查表只問結構的理由。
* **受測者沒有人可以問 Step 1 的問題。** 既有的那次跑動，版型與資料來源都是由人回答的。
  P1 步驟 2 把這個限制轉成一項結果，而非假裝它不存在。
* 全部跑動都用本機 jar，不涉及發布。下載路徑仍屬 P0-1b。
* **本計畫與受測者同 repo。** 技能是以符號連結掛進 `~/.claude/skills/zul-writer` 的，設計稿也在
  本 repo，所以受測者本來就讀得到這裡。改放同 repo 並未新增一個原本不存在的風險 —— 「不同 repo」
  從來不是真的屏障，子代理讀得到任何被交給它的路徑。真正的對策是**依敏感度分放**：本計畫進版控
  （受測者沒有理由去開一份規劃文件），檢查表、題目與負對照則只寫進 `tasks/eval-private/`，
  被讀到即致命，所以不進版控。

## 已定位並已修正的重複現象

XML 註解不得含 `--`，已**三次**獨立發生：既有跑動的分隔線註解、本工程 8/24 的素材撰寫、
8/25 的對照素材撰寫。**這是目前唯一達到「重複即訊號」門檻的項目**，成因已定位，源頭修正
已提交（`agent-skill` 的 `3d485f2`）。

*成因*：`references/controller-guidelines.md` **第 4 條**明文建議用 `// --- Wired components ---`
這種分隔註解。在 Java 合法，在 ZUL 是硬錯誤，而沒有任何一份參考文件講過這個差別 —— 技能
自己教出了這個習慣。（本文件先前誤記為第 10 條，見 Change Log。）

*源頭修正，兩處*：

* `controller-guidelines.md` 第 4 條**保留** Java 的分隔線建議，只補上「此風格僅限 Java，
  XML 不許」的對比。刪掉 Java 建議等於用一個壞指示換掉另一個 —— 缺的是對比，不是那條建議。
* `SKILL.md` 的 Step 2 產生準則**另外獨立寫一次**這條規則。理由：寫靜態頁的代理不會打開
  `controller-guidelines.md`，規則必須在真正寫 ZUL 的那一側也存在。

*診斷訊息*：驗證器本來就攔得下來（Layer 1 XML 檢查），但 expat 只說
`not well-formed (invalid token)`，沒有指向真正的規則。08-25 已在 `validate-zul.py` 的
`ParseError` 處理路徑補上具名提示，實測輸出：

```
Layer 1: XML Well-formedness... ✗ FAIL
  XML syntax error: not well-formed (invalid token): line 3, column 8 ...
  Line 3: <!-- ---------- left column ---------- -->
  Hint: Line 3 has '--' inside an XML comment. XML forbids that anywhere
        between <!-- and -->. Use '=' for separators: <!-- ===== left column ===== -->
```

僅在既有失敗訊息上追加一行，不改變任何通過／失敗判定；正常頁面完全不受影響（實測
`healthy-page.zul` 仍為 `✓ All validations passed`，單一 `-` 不觸發）。

*修正後的回歸實測*：命令列合約 **20 項全過、離開碼 0**；語料庫 **32 檔、0 回歸、0 過期、
0 孤兒、6 仍隔離**。兩套件都是在上述變更**之後**重跑的結果，不是變更前的舊數據。
